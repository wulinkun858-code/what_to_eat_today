# 多角色点餐系统 · 产品与技术设计（v1 规划）

> 2026-10-01 起草。将「坤坤菜单」从个人菜谱升级为三角色点餐系统：
> **超级管理员 / 厨师（由普通用户升级）/ 普通用户（食客）**。
> 参考市场模式：食堂报餐（无价格无份数的意向报餐）、点餐订单状态机、厨房端新单通知（KDS 思路）。

---

## 1. 角色与权限矩阵

| 能力 | 食客（默认） | 厨师 | 超级管理员 |
|---|---|---|---|
| 浏览菜单 / 搜索 / 评论 | ✅ | ✅ | ✅ |
| 创建/编辑菜品 | ❌ | ✅（仅自己的） | ✅（全部） |
| 点单（选菜提交报餐单） | ✅ | ✅（也可以吃） | ✅ |
| 查看自己的订单 | ✅ | ✅ | ✅ |
| 收到新订单消息 | ❌ | ✅（含自己菜的订单） | ✅ |
| 制作列表（加入/完成） | ❌ | ✅（自己的） | ✅（查看全部） |
| 取消订单 | ✅（仅待处理） | ❌ | ✅（任意） |
| 查看全部订单 | ❌ | ❌ | ✅ |
| 用户角色管理（升厨师/降级） | ❌ | ❌ | ✅ |

- 角色存于 `profile.role`：`diner`（默认）/ `chef` / `admin`
- **管理员唯一**（当前 openid）；厨师可有多个；升级路径：食客 → 厨师（管理员操作）

## 2. 核心业务流程

```
食客                        系统                          厨师
 │ 浏览菜单(全部菜品公开)      │                             │
 │ 选「想吃」→ 点菜单          │                             │
 │ 提交报餐单 ──────────────→ │ 校验菜品存在                 │
 │                           │ 生成订单(待处理)             │
 │                           │ 按菜品的归属厨师分发消息 ───→ │ 消息列表看到
 │                           │                             │ 「谁想吃什么」
 │                           │                             │ 一键加入制作列表
 │ 我的订单：制作中            │ ←──── 状态变更 ───────────── │ 制作完成逐项打勾
 │ 已完成                     │ 全部完成 → 订单已完成         │
 └ 取消（仅待处理时）          │                             │
```

- **无价格、无数量**：订单条目是菜品集合（去重），纯意向报餐（食堂报餐模式）
- 一个订单可跨多个厨师的菜 → **按厨师拆分消息**，各厨师只看到自己被点的菜

## 3. 订单状态机（参考市场标准，去掉支付环节）

```
待处理(pending) ──厨师加入制作列表──→ 制作中(cooking) ──全部条目完成──→ 已完成(done)
      │
      └──食客取消(canceled)※仅待处理可取消；管理员可取消任意状态
```
- 状态变更由**云函数**执行（带角色与归属校验），杜绝客户端越权
- 变更同时写订单日志字段（statusHistory: [{status, time, by}]），便于追溯

## 4. 数据模型

### 4.1 profile（升级为用户身份表）
```
{ _id: <openid>（改为以 openid 作主键，便于安全规则 get() 角色判断）,
  nickname, avatarFileID,
  role: 'diner' | 'chef' | 'admin',
  createdAt, updatedAt }
```
- 现有 profile 文档（自动 _id）一次性迁移为 _id=openid
- **管理员引导**：若集合中不存在 admin，第一个打开小程序的用户自动认领（或由控制台直接写入指定 openid，二选一）

### 4.2 dishes（菜单 → 对全体登录用户公开）
```
现有字段不变；_openid 语义 = 制作该菜的厨师
```
- **安全规则变更**：read 从「仅本人」→「所有登录用户」（菜单公开展示，这是点单的前提）
- create：仅 chef/admin；update/delete：本人或 admin

### 4.3 orders（报餐单）
```
{ _openid: <食客openid>,
  items: [{ dishId, dishName, dishImage, chefOpenid }],  // 冗余快照，菜删了单还在
  chefOpenids: [<openid>...],                            // 参与厨师去重集合
  status: 'pending' | 'cooking' | 'done' | 'canceled',
  statusHistory: [{ status, time }],
  createdAt, updatedAt }
```

### 4.4 messages（厨师消息）
```
{ _openid: <厨师openid>,        // 收件人
  type: 'new_order',
  orderId, orderStatus,
  dinerNickname,                // 冗余，谁点的
  items: [{ dishName }],        // 被点的自己的菜
  read: false,
  createdAt }
```
- 食客提交订单时由云函数按 `chefOpenids` 扇出；「我的」tab 显示未读红点

### 4.5 cooklist（厨师制作列表）
```
{ _openid: <厨师openid>,
  dishId, dishName,
  orderId, dinerNickname,      // 来源订单（可空 = 厨师主动加的菜）
  done: false,
  createdAt, doneAt }
```
- 厨师从消息「一键加入」，也可从菜单主动添加；逐项打勾完成
- 同一订单的全部条目完成时，云函数自动把订单推进到「已完成」

## 5. 特权操作边界（云函数，防越权的关键）

客户端安全规则继续管「本人的数据」；**跨用户/角色相关一律走云函数**（`getWXContext().OPENID` 服务端验角色）：

| 云函数 | 调用方 | 职责 |
|---|---|---|
| `orderCreate` | 食客 | 校验菜品存在与可见 → 建订单 → 扇出厨师消息 |
| `orderAction` | 食客/厨师/管理员 | 取消（食客限待处理）/ 状态推进（校验菜品归属厨师） |
| `cooklistAction` | 厨师 | 加入/完成制作条目（校验菜品归属）；联动订单状态 |
| `roleManage` | 管理员 | 用户列表、设置角色（唯一授权入口） |
| `adminView` | 管理员 | 全部订单 / 全部制作列表 / 统计 |

客户端规则保持：dishes（读公开/写本人）、messages、cooklist、orders（本人读写），
orders 的厨师侧读取通过 messages 冗余实现，不开放跨用户读。

## 6. 页面与交互（按角色差异化）

| 页面 | 食客看到 | 厨师额外看到 | 管理员额外看到 |
|---|---|---|---|
| 首页(菜单) | 搜索 + 轮播 + 品类滑动条（管理员定义）+ 卡片「+ 想吃」→ 点菜单 | 同食客 + 「管理我的菜」入口 | 全部 + 管理入口 |
| 评论 tab | 不变 | 不变 | 不变 |
| 我的 | 昵称/头像 + 我的订单 | + 厨师工作台（消息红点） | + 用户管理 / 全部订单 |
| 新增页 | 点菜单确认页；我的订单（状态/取消） | 厨师工作台（消息列表 → 一键加入制作列表；制作清单 → 打勾完成） | 用户管理（角色升降）；全部订单 |

## 7. 分期落地（每期可独立验收）

- **P1 角色基座**：profile 迁移（_id=openid + role 字段）、管理员引导/认领、角色读取服务、
  我的页按角色显隐入口、（云函数 roleManage + 用户管理页）
- **P2 菜单公开 + 点单**：dishes 读规则放开、首页「想吃」点菜单、点菜单确认页、
  云函数 orderCreate、我的订单列表（含取消）
- **P3 厨师侧闭环**：云函数扇出消息、厨师工作台（消息+制作列表）、状态机推进（orderAction/cooklistAction）、
  食客订单状态可见、tab 红点
- **P4 管理员视图**：全部订单、全部制作列表、运营统计

## 8. 关键决策点（待确认）

1. **管理员引导方式**：A. 首个打开小程序者自动认领 admin；B. 你提供 openid，控制台直接写入（更稳妥）
2. **菜单公开**：菜品对所有登录用户可见（点单前提，个人日记属性让位于餐厅菜单属性）——需你确认
3. **存量菜品归属**：现有菜品的 _openid 是你自己（admin），其被点单时消息发给你本人
4. 首期范围：P1+P2 先行，还是四期连做
